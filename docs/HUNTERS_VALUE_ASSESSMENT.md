# Hunters 文档价值深度评估

## 🔍 逐文档价值分析

---

## 1. orchestrator.md 价值评估

### **有价值的内容：**

#### **1.1 任务分解思维** ⭐⭐⭐⭐
```markdown
工作流：
1. 识别攻击面（目标范围）
2. 拆分子任务（按领域/endpoint）
3. 派发执行（派给专门的 Agent）
4. 汇总结果（整合所有发现）
```

**价值：** 通用的任务编排思维，适用于所有领域
- ✅ 可迁移到新架构的 Orchestrator 设计文档
- ✅ 任务分解策略通用（不限安全）

---

#### **1.2 防幻觉纪律** ⭐⭐⭐⭐⭐
```markdown
纪律：
- 报告必须与实际落库一致（数量、id 对得上）
- 不夸大、不臆造未验证的内容
- 受限/失败如实说，别用"已全面覆盖"掩盖缺口
- 不凭记忆写，必须引用实际证据
```

**价值：** 极高！防止 LLM 幻觉的核心原则
- ✅ **跨领域通用**（数据分析、代码生成都适用）
- ✅ 应该提取到新架构的核心原则文档

---

#### **1.3 子任务派发原则** ⭐⭐⭐⭐
```markdown
派活要具体：
- 含糊的 task 会让子代理空转
- 派突破类子代理时锁定一个明确攻击面
- 带上上下文（凭据/情报共享）
```

**价值：** 高，通用的 Agent 协作原则
- ✅ 可迁移：清晰的任务描述 = 高效执行
- ⚠️ 但需要去掉安全术语（"攻击面" → "工作范围"）

---

### **无价值/过时的内容：**

❌ **工具列表**（read_findings, search_corpus 等）→ API 已变更
❌ **Agent 角色定义**（planner vs orchestrator）→ 架构已不同
❌ **安全专用术语**（扫描、编排者、打穿、战果）→ 不符合中性原则

---

## 2. reconnaissance.md 价值评估

### **有价值的内容：**

#### **2.1 探索策略** ⭐⭐⭐
```markdown
探索顺序：
1. 先看已有数据（流量、凭据、历史发现）
2. 主动探测（目录、参数、技术栈）
3. 重放验证（改请求看响应差异）
4. 结构化输出（清单：endpoint × 参数 × 方向 × 优先级）
```

**价值：** 中等，有些通用
- ✅ "先看已有再探索" 是通用策略
- ⚠️ 但具体探测方法（目录扫描、参数爆破）是安全专用

---

#### **2.2 信息分类思维** ⭐⭐⭐⭐
```markdown
区分两类来源：
① 有真实流量的（高保真，可直接 replay）
② 仅爬虫发现的路径/参数（线索，需结合真实流量构造测试）
```

**价值：** 高，数据质量分级思维
- ✅ 通用：高保真数据 vs 待验证线索
- ✅ 可迁移：数据分析、代码审查都需要区分数据来源可信度

---

### **无价值/过时的内容：**

❌ **安全工具列表**（subfinder, httpx, katana, nmap 等）→ 安全专用
❌ **Web 专用流程**（目录扫描、WAF 识别）→ 不适用其他领域
❌ **攻击面清单格式**（endpoint × 可疑参数 × 漏洞方向）→ 安全专用

---

## 3. exploitation.md 价值评估

### **有价值的内容：**

#### **3.1 验证方法论** ⭐⭐⭐⭐⭐
```markdown
验证铁律：
1. 必须有可复现的证据（不能只靠工具输出）
2. 区分"可能存在"和"确认可利用"
3. 依赖链清晰表达（前置条件 → 当前步骤）
4. 动态值处理（服务器现造值用 resolve）
```

**价值：** 极高！验证思维通用
- ✅ **跨领域通用**：
  - 数据分析：必须有可复现的查询
  - 代码生成：必须有可运行的测试
  - API 测试：必须有实际响应证据
- ✅ **核心原则**：可复现 > 工具输出

---

#### **3.2 证据收集规范** ⭐⭐⭐⭐⭐
```markdown
finding 必须：
1. 锚定来源（哪条流量 id）
2. 提供复现步骤（repro）
3. 断言前先确认（view_traffic 确认响应真的有 X）
4. 不用记忆里的默认值（一律以实际数据为准）
```

**价值：** 极高！防幻觉核心
- ✅ **必须提取**到新架构核心原则
- ✅ 完全通用（所有领域都需要证据链）

---

#### **3.3 失败处理原则** ⭐⭐⭐⭐
```markdown
反模式：
❌ 401/403 直接放弃 → 调 read_credentials 拿对的 token 重试
❌ 工具误报直接信 → 人读响应确认
❌ 单条测试不过直接放弃 → 尝试变体/绕过
```

**价值：** 高，韧性执行思维
- ✅ 通用：遇到失败不放弃，尝试其他路径
- ✅ 可迁移：API 调用失败 → 重试/降级

---

### **无价值/过时的内容：**

❌ **漏洞利用工具**（sqlmap, dalfox, ysomap 等）→ 纯安全
❌ **漏洞类型枚举**（SQLi, XSS, RCE 等）→ 安全专用
❌ **Payload 示例**（各种注入 payload）→ 安全专用

---

## 4. traffic-analysis.md 价值评估

### **有价值的内容：**

#### **4.1 从结果反推输入的思维** ⭐⭐⭐⭐
```markdown
分析策略：
1. 看响应异常（不是看请求）
2. 从响应线索反推可控点
3. 跨请求关联（会话/越权需要比对多条）
```

**价值：** 高，逆向分析思维
- ✅ 通用：数据分析中也需要从结果反推原因
- ✅ 可迁移：日志分析、性能调优

---

#### **4.2 证据锚定** ⭐⭐⭐⭐⭐
```markdown
铁律：
- finding 必须锚定来源流量 id
- 断言"响应泄露了 X" 前，先 view_traffic 确认
- host / endpoint 以实际列出的为准，不用记忆
```

**价值：** 极高！与 exploitation.md 一致
- ✅ 必须提取到核心原则

---

### **无价值/过时的内容：**

❌ **mitmproxy 流量专用**（只适用 Web 流量分析）
❌ **Web 漏洞检测**（SQLi, XSS, IDOR）→ 安全专用

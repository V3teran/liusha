# liusha v1.1 设计规范

> 取代 `2026-04-28-liusha-v1-design.md`。本文档为 liusha v1.1 的最终设计基线。

## 1. Goal

将 v1 重构为「**1 流量 → 1 主 ReAct + 同进程嵌套子 ReAct（按 skill 切上下文）**」+ **启发式驱动** 的架构。

具体目标：

- **统一入口**：每条流量只对应 1 个主 ReAct（traffic mode），不再切窗、不再产出 2 层 Asynq task。
- **同进程嵌套**：子 ReAct 通过 `spawn_skill` 工具在 **同一进程内** 启动，按 skill（如 `bac`、`sqli`）切上下文，避免跨进程 RPC。
- **启发式前置**：在入队前用基于规则的打分器过滤明显无意义的流量（静态资源等），把 LLM 算力留给可能存在漏洞的入口。
- **修复并发 bug**：v1 的 LLM Generator Factory 把 `tools` 在构造时绑定 + 缓存，导致跨任务 tools 错乱；v1.1 改为 ClientPool（HTTP 层单例）+ 无状态 Generator。
- **业界规范命名**：模块名向业界 pentest / agent 工具的通用词靠拢（scanner、ingestor、tool）。

## 2. 与 v1 差异

| 维度 | v1 | v1.1 |
| --- | --- | --- |
| 任务层级 | sniffer task → BAC subtask（**Asynq 跨进程**） | 1 主 task → spawn_skill 嵌套子 ReAct（**同进程**） |
| 切窗 | 有 `traffic_window` 表 + 时间窗聚合 | **无**，1 flow = 1 主 task |
| 子任务并发 | Asynq 多 worker 抢消费 | 主 LLM 一轮返多个 spawn_skill → **runtime 自动 goroutine 并行** |
| 启发式 | 无，所有流量入队 | 入队前打分，score >= 30 才入队 |
| 队列数 | `agent:dispatch` + `agent:react` 双队列 | **单一 `agent:react`**，`agent:dispatch` 保留备用 |
| LLM Client | Factory 缓存 Generator（绑定 tools） | ClientPool 缓存 Client（HTTP 层），Generator 无状态 |

## 3. Architecture

```
┌──────────┐  HTTPS  ┌─────────┐  Redis Stream  ┌──────────────────────┐
│  Proxy   │────────▶│  Stream │───────────────▶│ ingestor (启发式打分)  │
│ (mitmproxy)│       │ flow:raw│                │  score >= 30 ?         │
└──────────┘         └─────────┘                └──────────┬───────────┘
                                                            │ Asynq Enqueue
                                                            ▼
                                              ┌──────────────────────────┐
                                              │  Asynq queue: agent:react │
                                              └──────────┬───────────────┘
                                                         │ Dequeue (Concurrency=6)
                                                         ▼
                              ┌──────────────────────────────────────────┐
                              │  cmd/scanner (worker 进程, N 实例)         │
                              │  ┌──────────────────────────────────────┐ │
                              │  │  主 ReAct (mode=traffic)              │ │
                              │  │   tools: classify_traffic /          │ │
                              │  │          spawn_skill / get_findings  │ │
                              │  │          read_state / write_*  / done│ │
                              │  └──┬───────────────────────────────────┘ │
                              │     │ spawn_skill (同进程, 多个时并发 goroutine)│
                              │     ▼                                      │
                              │  ┌──────────────────────────────────────┐ │
                              │  │  子 ReAct (skill=bac)                 │ │
                              │  │   tools: fetch_creds / replay /      │ │
                              │  │          diff / heuristic_match      │ │
                              │  │          + common (read/write/done) │ │
                              │  │   写 finding → PG                     │ │
                              │  └──────────────────────────────────────┘ │
                              └──────────────────────────────────────────┘
                                                         │
                                                         ▼
                                              ┌──────────────────────┐
                                              │   PostgreSQL (PG)     │
                                              │   - finding           │
                                              │   - agent_task        │
                                              │   - engagement(.hint) │
                                              │   - graph_node/edge   │
                                              └──────────────────────┘
```

数据流：`proxy → Stream → ingestor 启发式 → Asynq main queue → scanner 主 ReAct → spawn_skill 嵌套 → 子 ReAct → finding`。

## 4. 模块命名规范

向业界 pentest / agent 工具的通用词对齐：

| v1 路径 | v1.1 路径 | 选词理由 |
| --- | --- | --- |
| `cmd/agent-worker` | `cmd/scanner` | 业界 pentest 工具（nuclei、nikto、wpscan）惯用 scanner |
| `internal/flowconsumer` | `internal/ingestor` | 流量摄入 + 启发式过滤，ingestor 是数据管道通用词 |
| `internal/agent/runtime` | `internal/react` | 直接命名为 ReAct 模式，去除歧义 |
| `internal/agent/action` | `internal/tool` | OpenAI / Anthropic API 标准词是 tool（不是 action） |
| `internal/agent/actions/{common,bac}` | `internal/tools/{common,vuln/bac}` | tools 复数 + vuln/ 子命名空间为后续 sqli / xss 留位 |

## 5. 启发式打分（Explorer 前置）

ingestor 在入队前对每条 flow 打分，决定是否入主队列。

| 规则 | 分值 |
| --- | --- |
| 静态资源（`.js .css .png .jpg .ico .woff .svg .map` 等） | **0** |
| 路径含 `/admin/` `/sys/` `/manage/` | **+30** |
| 路径含 `/api/user/` `/profile` `/me` | **+20** |
| 路径含 `/order/` `/account/` `/wallet/` | **+20** |
| 参数含 `uid` `user_id` `order_id` `account_id` `customer_id` 等身份性参数 | **+25** |
| 方法为 `POST` / `PUT` / `DELETE` | **+10** |
| 携带 `Cookie` 或 `Authorization` 头 | **+10** |

**入队阈值**：`score >= 30` 才入 `agent:react` 队列；其他丢弃并记 metric。

> 启发式只是「门票」，不替代 LLM 判定 —— 进入主 ReAct 后仍由 `classify_traffic` 二次判流量类型与候选漏洞清单。

## 6. 主 ReAct 工具集（mode=traffic）

| 工具 | 作用 |
| --- | --- |
| `classify_traffic` | LLM 判定流量类型（业务接口 / 静态 / 三方）+ 输出候选漏洞清单（如 `["bac","sqli"]`） |
| `spawn_skill` | **同进程嵌套**启动子 ReAct；多个时 runtime 自动用 goroutine 并发调度 |
| `get_findings` | 查 PG，按 `engagement_id` / `flow_id` / `task_id` 过滤当前发现 |
| `read_state` | 读取主 ReAct 自身的 fact / idea / graph + engagement 注入的 memory_hints |
| `write_fact` | 写一条事实（path / param / behavior 等观察） |
| `write_idea` | 写一条假设 / 推测 / 下一步思路 |
| `write_graph` | 写 attack DAG 节点或边（语义：从 entrypoint 推进到 finding 的攻击路径） |
| `done` | 终止主 ReAct，写汇总 |

## 7. 子 ReAct 工具集（skill=bac）

子 ReAct 上下文按 skill 切片，工具分两层：

**common（所有 skill 共用）**：

| 工具 | 作用 |
| --- | --- |
| `read_state` | 读自己的 fact / idea + 主 ReAct 透传的上下文片段 |
| `write_fact` | 写事实 |
| `write_idea` | 写假设 |
| `write_finding` | **核心产出**：写 finding 到 PG（包含 evidence、severity、复现 payload） |
| `done` | 终止子 ReAct，必须由 `done_validate(BACValidator)` 通过 |

**bac（skill=bac 专属）**：

| 工具 | 作用 |
| --- | --- |
| `fetch_creds` | 取目标 engagement 的 A / B / 匿名身份凭据（cookie / token） |
| `replay` | 用替换的身份重放原始请求 |
| `diff` | 对比 baseline 和 replay 的响应（状态码 / 长度 / 关键字段） |
| `heuristic_match` | 用规则判越权特征（金额、姓名、订单号回显等） |

## 8. Payload 格式（保留整站模式扩展口子）

```go
// internal/types/payload.go
type Payload struct {
    TaskID       string          `json:"task_id"`
    EngagementID string          `json:"engagement_id"`
    Mode         string          `json:"mode"`        // "traffic" | "site"
    Entrypoint   json.RawMessage `json:"entrypoint"`  // 按 mode 解析
}

// mode=traffic → entrypoint 反序列化为：
// { "flow_id": "...", "host": "...", "url": "...", "method": "GET" }

// mode=site → entrypoint 反序列化为（v1.5 启用）：
// { "start_url": "https://target.com" }
```

`Mode` 字段是为 v1.5 整站爬取模式预留的扩展口；v1.1 只实现 `mode=traffic`，遇到 `mode=site` 直接 `return ErrUnsupported`。

## 10. hint 复用路径

**写路径**（finding → hint）：

1. 子 ReAct `write_finding` 落 PG。
2. 触发 `distill` hook（同进程异步 goroutine），LLM 蒸馏出可复用的攻击模式片段（如 "/api/user/{uid} 直接传 uid 参数无校验"）。
3. 蒸馏结果 `UPDATE engagement.memory_hints` 追加。

**读路径**（hint → 主 ReAct）：

1. 主 ReAct 启动时，system prompt 自动注入当前 `engagement.memory_hints` 列表。
2. 主 ReAct 任意步调用 `read_state` 时，返回值同样包含最新的 memory_hints。

效果：同一 engagement 内的 finding 经验，能在后续 flow 的主 ReAct 中被复用，不必重新探索。

## 11. LLM Client 单例

修复 v1 的并发 bug：v1 `Factory` 缓存的是 `Generator`，且 Generator 在构造时绑定 `tools`，导致两个 task 用同一份 Generator 时 tools 被互相覆盖。

v1.1 拆成两层：

```go
// 1) ClientPool: HTTP 层单例（线程安全，按 provider+model 缓存）
type ClientPool struct {
    openaiClients    sync.Map // key=model → *openai.Client
    anthropicClients sync.Map // key=model → anthropic.Client
}

func (p *ClientPool) OpenAI(model string) *openai.Client { /* ... */ }
func (p *ClientPool) Anthropic(model string) anthropic.Client { /* ... */ }

// 2) Generator: 无状态，每个 ReAct 实例自建一个，tools 在 Generate 时传入
type Generator struct {
    client SomeProviderClient // 从 ClientPool 取
    model  string
}

func (g *Generator) Generate(ctx context.Context, msgs []Message, tools []Tool) (*Response, error) {
    // tools 是参数，不是字段 → 不会跨 task 错乱
}
```

**关键约束**：`Generator` 不持有 `tools` 字段；`tools` 只在 `Generate` 调用时作为参数传入。

## 12. Middleware 链

ReAct loop 在每步 LLM 调用前后跑一串 middleware。v1.1 链路精简：

| ReAct 类型 | middleware 链（外层 → 内层） |
| --- | --- |
| 主 ReAct（mode=traffic） | `result_compress` → `done_validate(nil = AlwaysOK)` |
| 子 ReAct（skill=bac） | `result_compress` → `done_validate(BACValidator)` |

- `result_compress`：把超长 tool result 截断 / 摘要（保留 head + tail + length）。
- `done_validate(v)`：拦截 `done` 工具调用，由 validator `v` 决定是否真正终止；`v=nil` 等价于 AlwaysOK。
- `BACValidator`：要求至少有 1 条 `write_finding` 被调用过，否则强制 LLM 继续。
- **`LoopDetector` 已砍**：MaxSteps（硬上限）+ DoneValidator（软兜底）已足够，避免增加误判。

## 13. Reviewer

| ReAct 类型 | 是否启用 Reviewer |
| --- | --- |
| 主 ReAct | **启用** |
| 子 ReAct | 不启用（短任务无意义，最多十几步就 done） |

**主 ReAct Reviewer 行为**：

- 每 5 步触发一次 sidecar 评估。
- 用 `light_provider`（更便宜的小模型，如 GPT-4o-mini）+ **独立上下文**（不污染主 ReAct 的 message 历史）。
- 输出三选一：
  - `keep_going` —— 继续，无干预。
  - `steer_with_hint` —— 注入一条 hint 到主 ReAct 上下文（如 "你已经在 `/api/user/profile` 重复 3 次，试试 `/api/order/list`"）。
  - `abort_low_value` —— 强制 done（当前流量探索价值过低）。

## 14. 并发模型

| 层级 | 并发机制 |
| --- | --- |
| **进程级** | `cmd/scanner` 多实例（K8s replicas / docker compose scale），共同消费同一个 Asynq queue（`agent:react`） |
| **进程内** | `asynq.Concurrency = 6` —— 单进程 6 个 goroutine 并发跑 6 个主 ReAct |
| **单 ReAct 内** | runtime 在执行 LLM 一轮返回的多个 tool_calls 时，用 `goroutine + sync.WaitGroup` 并发；主 LLM 一轮返多个 `spawn_skill` 时，多个子 ReAct **自动并发**起来 |

调优要点：

- 单进程 6 并发是经验值，受 Postgres 连接池、Redis pipeline、LLM provider rate limit 共同制约。
- 子 ReAct 并发数受主 LLM 一轮 tool_calls 数量天然限制（通常 1-4 个），不需要额外限流。

## 15. Asynq 队列

| 队列名 | 用途 | 状态 |
| --- | --- | --- |
| `agent:react` | 主 ReAct 任务队列（所有 mode=traffic / mode=site 都进这里） | **唯一活跃队列** |
| `agent:dispatch` | v1 残留的 dispatcher 队列 | **保留备用**，v1.1 不投递；预留给未来 dispatcher 模式（如批量任务编排） |

队列优先级权重：`agent:react = 10`，`agent:dispatch = 1`（即便有任务也几乎不会被调度）。

## 16. DoD（Definition of Done）

v1.1 落地完成的判定标准：

1. **主 → 子流程通**：主 ReAct 收 1 条 flow，至少 spawn 出 1 个 BAC 子 ReAct（日志可验证 `spawn_skill skill=bac` 调用）。
2. **finding 落库**：子 ReAct 至少调用 1 次 `write_finding`；主 ReAct `done` 时通过 `get_findings` 能查到 ≥ 1 条 finding。
3. **并行验证**：主 LLM 一轮返多个 `spawn_skill`，日志时间戳显示多个子 ReAct **重叠执行**（不是串行）。
4. **e2e**：18 条预制流量灌入 → ingestor 启发式入队 ≥ 12 条 → 至少 1 个主 task 跑出 ≥ 5 条 BAC finding。
5. **LLM Client 单例验证**：scanner 进程内 6 个 task 并发跑，日志中**不出现** tools 错乱（即子 ReAct 不应能调用主 ReAct 才有的 `spawn_skill`，反之亦然）。

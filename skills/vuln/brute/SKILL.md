# 暴力破解 / 用户枚举

## 漏洞本质

应用允许对登录/认证端点**无限制重试**——无 ratelimit、无账号锁定、无验证码、无 CAPTCHA。这类漏洞让攻击者能慢速字典/凭证填充攻击。

## 挖掘方向（思路，不是步骤）

**唯一铁律**：暴力破解漏洞 = 端点**缺乏防护机制**。验证方法是用 ≥10 次故意错误尝试观察响应是否变化——**不变 = 漏洞**。

**不要在沙箱里真去跑字典爆破**：30s timeout + 100 req/s 撑死 100 次尝试，没意义；反而可能触发真实告警让目标方运维警觉。挖洞阶段**测的是机制不是爆破速度**。

下面是倾向性建议，不是规则：

- 流量已包含登录表单 → 直接照搬，只改 username/password 字段
- 测试用**故意错误**的密码（不是真实密码）—— 否则你测的是"密码正确性"而非"防护机制"
- 同时观察"错误用户名"vs"错误密码"的响应差异 → 可能附带用户枚举漏洞

## 判定原则（按优先级）

### 1. ≥10 次错误尝试后响应**不变** → 暴力破解漏洞（high）

- 状态码不变（一直 200 或一直 401）
- 错误消息不变
- 无 429 Too Many Requests / 无"账号已锁定" / 无验证码出现

这是**最常见**的暴力破解漏洞形态。

### 2. 用户枚举：错误用户名 vs 错误密码返回不同响应 → 附带漏洞（medium）

应用回显不同消息：

- 错误用户名："User not found"
- 错误密码："Invalid password"

让攻击者能枚举出真实账号。即使端点有 ratelimit，用户枚举仍是独立漏洞。

### 3. 时序型用户枚举：错误用户名 vs 错误密码响应时间差 > 50ms → medium

服务端对存在用户做密码 hash 比对（耗时），对不存在用户直接返回（瞬间）——通过响应时间区分。需要多次采样取中位数排除网络抖动。

### 4. 默认弱密码登录成功（如 admin/admin、admin/password）→ critical

技术上不是"暴力破解漏洞"而是"弱口令"，但实际效果相同（攻击者无成本登录）。

### 5. 响应在错误次数后立即变化 → 防护正常（无漏洞）

- 429 Too Many Requests / Retry-After 头
- 响应里出现"账号已锁定"/"请联系管理员"/"请输入验证码"
- 验证码 / CAPTCHA challenge

## 误报排除

- 仅做了 1-2 次尝试就下结论 → 无效证据
- 把 401 当成有防护——许多应用 401 但允许无限重试，**要看是否计数**
- "成功登录"不是漏洞证据（你只是密码猜对了，不证明端点缺防护）
- 服务端只对同 IP ratelimit，分布式 IP 攻击仍有效——但这超出基本测试范围

## write_finding 红线

evidence 必须包含：

- **尝试矩阵**：≥10 次错误尝试的请求列表，每条含 `{username, password, status, body 摘要}`
- **响应变化分析**：明确说"前 N 次响应字段 X 不变"（状态码 / 错误消息 / 头部）
- **用户枚举证据**（如适用）：错误用户名 vs 错误密码的响应对比
- **repro_cmd**：一条 for 循环 curl，别人能跑出同结果

summary ≤500 字单行：`Brute Force in /vulnerabilities/brute/ — no ratelimit / lockout after 10 failed attempts; user enumeration via response message diff`
